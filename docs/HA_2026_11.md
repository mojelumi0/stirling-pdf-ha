# Home Assistant 2026.11 and Marketplace readiness

## Scope and current evidence

This is a separate 0.3.1 preparation based on released main-line 0.3.0 at
`b434eb14409268e781dfaeeb4eda48cff759de79`. PR #11 and 0.4.0-alpha.1 remain
separate. The integration still supports one server and HA 2026.9.0 or newer.

| Check | State at preparation | What it does not prove |
|---|---|---|
| Official category, package layout and HACS metadata | Checked against official documentation | Public catalog acceptance |
| DeviceInfo keyword constructor and explicit flow step IDs | Present in the existing runtime | Passing tests on every HA version |
| Automatic 2026.9.0 and 2026.10.2 jobs | Preserved; new tests need new CI runs | Compatibility with 2026.11.0 |
| Manual 2026.11.0 job | Prepared, no matching test-package pin selected | A completed or successful 2026.11 job |
| Test Raspberry Pi | Maintainer reports HA 2026.11.0 with 0.4.0-alpha.1 and two servers | Installed 0.3.1, migration verification or PDF acceptance |

Never copy this single-server line over a multi-server development installation
without a separate, explicitly agreed test/restore plan. Do not delete entries
to make a test pass: that deletes the integration's local operation statistics.

## What is already compatible by construction

- `hacs.json` stays in the repository root with the 2026.9.0 minimum. Do not
  rename it to `marketplace.json` or list HA's own dependencies in the manifest.
- `DeviceInfo(...)` is built with keyword arguments in the shared entity base.
  That constructor works with the older TypedDict and the newer dataclass.
- Forms already pass their `step_id`. Keep doing so in future flows.
- Custom integrations may continue returning booleans from config-entry setup
  and unload. A switch to new Core-only helpers is not required here.
- Entity names use device context; the integration does not compose a full
  `friendly_name` itself. Existing IDs and unique IDs are not rewritten.
- No integration-owned add/remove hooks require a new entity-ID-change hook in
  this stable branch. The new rename tests exercise HA's lifecycle instead.

Optional monitoring entities with integration-owned add hooks exist in PR #11,
not here. Convert their device mappings and test their lifecycle separately when
that work resumes. Do not assume tests in this single-server branch cover them.

## CI dependency gate

The published test package checked on 2026-11-04 was
`pytest-homeassistant-custom-component==0.13.375`, requiring
`homeassistant==2026.10.4`. It cannot validate 2026.11.0 by simply changing the
matrix label. No guessed future package version is committed.

When an upstream release supports the exact stable Core version:

1. Verify its dependency metadata on
   [PyPI](https://pypi.org/project/pytest-homeassistant-custom-component/).
2. Once this workflow exists on the default branch, open GitHub **Actions >
   Home Assistant 2026.11 readiness > Run workflow**. Select the intended branch
   and enter the exact compatible test-package version. GitHub requires a
   dispatchable workflow to exist on the default branch first.
3. Pip must install both exact versions with the normal resolver and `pip check`.
   A dependency conflict is a failure, not a reason to use `--no-deps` or
   override the upstream Home Assistant requirement.
4. Confirm the installed-version assertion, full HA suite, per-module coverage
   checker, Ruff and formatting all pass. Keep the run URL and tested commit.
5. Pin that verified package in a separate requirements file and add 2026.11.0
   to the existing automatic matrix. Retain the minimum-version job and the
   required aggregate `pytest` status name and coverage targets.

Until step 4 is complete, label 2026.11 as prepared/pending, not verified. Do not
require the preparatory manual status check in a branch ruleset: it intentionally
does not run on ordinary pushes or pull requests yet. Older green jobs do not
validate new code in this branch.

## Marketplace migration check on the test Raspberry Pi

These are manual checks, not actions performed by this preparation. Wait for the
maintainer to confirm the intended MCP connection and authorize any live changes.

1. Keep a Home Assistant backup. Record the installed integration version,
   each server entry and entity ID, operation count, last operation and timestamp.
   Do not include credentials or private URLs in public evidence.
2. Open **Settings > Marketplace** as an administrator. Read the risk notice;
   do not treat installation of community code as a Home Assistant security audit.
3. Confirm this repository remains installed after migration and that its update
   entity retains its ID. Do not remove/reinstall HACS or Stirling PDF as part of
   this check. Existing custom repositories should be carried over automatically.
4. Confirm the repository's available release, release-notes link and brand
   image. A correct integration icon alone does not prove the update card works.
5. For alpha testing only, open **Settings > Devices & services > Marketplace**,
   the repository device, enable the disabled **Pre-release** entity and turn on
   its switch. This is an explicit user choice, not a default we change remotely.
6. Compare the recorded integration entities and statistics. A migrated update
   entity is separate from our server-status entities and must not reset them.

This checks Marketplace behavior with whichever integration version is actually
installed. It does not count as a 0.3.1 acceptance run if 0.4.0-alpha.1 is loaded.

## Acceptance of this single-server branch

Use a separate approved HA 2026.11.0 instance, or agree a backup-based plan
first. Check the actual installed version in diagnostics, not only a script's
user-entered version label. Do not migrate or downgrade the two-server test
installation just to run this checklist.

- Execute the native `examples/ha_test.yaml` against a standalone API-key server
  and the Community App in separate single-server setups. Keep `/config/pdf-test`
  and copies of `a.pdf` and `b.pdf`. Enable page extraction in the test.
- Inspect all outputs and exact rejection reasons. A REJECTED report alone
  cannot distinguish a validation failure from a connection failure.
- Check masked unchanged credentials, sanitized diagnostics and retained entity
  IDs. Compare statistics after integration reload and HA restart without
  rerunning the PDF script. Authorize those live actions separately.
- If testing display/ID renaming manually, use a disposable entity and record its
  previous ID. Updating IDs can break references in user automations. Do not
  rename real entities automatically. CI performs isolated registry-renaming
  tests without touching live Home Assistant.
- Use integration-specific debug logs and action history for diagnosis, but
  inspect every export for credentials, private paths and document information
  before sharing. Do not assume an editor's masked field redacts every history.

## Publishing boundaries

This work does not submit a catalog PR, merge PR #11, create a GitHub release,
install an integration, expose a port, configure an MCP server or restart HA.
All of those remain separate, explicitly authorized steps. A Marketplace custom
repository is not an official Core integration or a Bronze/Silver/Gold award.
